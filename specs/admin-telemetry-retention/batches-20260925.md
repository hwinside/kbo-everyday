## Transaction boundaries

`cron -> batch RPC (oldest day/PV) -> batch RPC (oldest day/dwell)
      -> batch RPC (done) -> rollup RPC`

Each arrow is a separate request/commit. Every raw batch selects the oldest
eligible **complete KST date of one raw kind**, validates its coverage and deletes
it under the same transaction and retention advisory/table locks. No arbitrary
row LIMIT or reuse of a preview from a previous transaction. PV has its traffic
and user-day checks; dwell has daily totals, session-count and session-distribution
checks. Unselected-kind candidates are empty. The existing all-kind preview is a
wrapper over the same scoped implementation, and existing callers retain their
contract. Cross-midnight dwell sessions are still reconciled by complete daily
slices, as in the existing oldest-day catch-up.

The `LIMIT 1` selects one of two oldest-date metadata rows, **not raw rows**.
Locks use NOWAIT/try-advisory and are released at each commit. Fresh physical
backup metadata is fetched by the route; each DB batch revalidates its age against
wall-clock time (not the synthetic preview date).

Rollup cleanup runs in a separate transaction, only after an authoritative empty
raw result. It rechecks that no eligible raw remains under the same locks. All
existing 365-day cleanup rules and lifetime activation preservation remain.

## Partial progress, errors and audit interpretation

- `admin_telemetry_retention_runs.phase`: `legacy_full` (existing callers),
  `raw_batch`, or `rollup_cleanup`. `batch_day`/`raw_kind` identify partial commits.
- A `raw_batch.raw_cutoff` means that **kind** was purged through that cutoff;
  it must NOT be interpreted as both raw tables having advanced. Use phase/kind,
  the explicit `done` result, and actual raw minima for overall completion.
- Every nonempty raw batch has its own atomic count check + audit insert.
  Empty requests do not create duplicate raw audits. Rollup audit records its
  separate phase and all deletion counts.
- Error/timeout/ambiguous transport stops the invocation immediately. No retry.
  Logs retain acknowledged audit IDs and deletion totals. An unacknowledged
  commit may still exist: inspect DB audits/minima before manual replay.
- A later scheduled invocation selects remaining raw in the DB. It neither
  repeats acknowledged batches nor requires a client cursor.
- Success requires explicit raw `done` **and** committed rollup cleanup. Time or
  call budget exhaustion is an error with partial progress, never false success.
- Route budget is 35s with >=10s required before a new RPC, max 8 raw calls,
  10s request abort, plus <=8s backup lookup, within maxDuration=60s.

## Residual bounds

A single raw kind/day is still finite but not row-capped. Extreme future daily
volume can exceed 8s; that fails closed. This change removes the additive PV+dwell
validation/deletion cost from one request, not an unlimited-volume guarantee.
Independent production-path latency verification remains a rollout gate.
