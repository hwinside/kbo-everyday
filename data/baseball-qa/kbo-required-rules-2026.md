## 적용 순서·검증

1. 원문·코드·QA 진단을 PR로 제출하고 삼식 exact SHA GO를 받는다. 하린아빠에게 그 SHA 머지와 위 2개 source·18청크 운영 적용을 하나의 구체적 범위로 제시한다.
2. 승인된 코드 배포가 READY이고 도메인·merge SHA가 연결됐는지 확인한다. 코드만 배포된 상태를 수치 답변 복구 완료라고 하지 않는다.
3. 적용 직전 기존 10개 source의 revision·generation·identity·활성 content/embedding/metadata 지문을 재조회하고 보충 key 2개가 비어 있는지 확인한다. 예상 밖 변경이면 적용하지 않고 해당 변경을 대조한다.
4. 보호된 Gateway egress로만 로더를 --protected-egress --apply 실행한다. 정확한 JSONL·manifest·전용 state를 지정한다. 외부 임베딩 대상은 위 공식 원문 18청크뿐이며 사용자 질문/개인정보는 보내지 않는다. 현행 768차원 모델, 배치 16 기준 문서별 총 2배치가 예상된다.
5. 문서별 claim/활성화는 원자적이지만 2문서 전체는 하나의 트랜잭션이 아니다. 부분 실패 시 실제 상태·lease·완료지점을 먼저 확인한다. READY 동일 revision은 검증 후 건너뛰며 무조건 재임베딩하지 않는다.
6. 기존 10개 source·9,132청크 지문 불변, 보충 source 6/12청크·정확 revision·768차원·공식 URL/조항을 확인한다. 크론/전문서 refresh는 호출하지 않는다.
7. 삼식이 변이/회귀 검증과 실제 검색·모델 답변, 전용 계정 UI로 정규 11회·PS 15회·상위 5팀·FA 시점조건을 확인한다. 과거 기록/다른 대회 혼입과 일반 질문 회귀를 함께 본다. 서비스키 DB 조회만으로 End-User PASS 처리하지 않는다.

## 롤백·마감

- 새 source만 tombstone해 서빙에서 제외한다. data/baseball-qa/kbo-required-rules-2026.rollback.sql은 identity·PDF hash·revision·lease를 확인하며 기존 source는 update/delete하지 않는다. 원문·벡터를 보존해 조사 가능하다. 부분 적용에서는 활성 lease가 끝난 뒤 실제 상태를 확인하며 강제 lease 탈취는 하지 않는다.
- 코드 문제가 남으면 해당 PR revert를 별도 변경으로 처리한다. 데이터 롤백만으로 기존 10개 source 서빙 집합은 그대로 남는다. 승인되지 않은 다른 코퍼스를 대신 활성화하지 않는다.
- 실패 시 복구 완료 대신 HOLD와 실제 미검증 층위를 남긴다. PASS 후 Notion 배포/릴리즈·위키·TaskFlow와 일일 재분석 원장을 연결한다. 기존 매일 11:30 KST 크론은 유지하며 중복 예약하지 않는다.
